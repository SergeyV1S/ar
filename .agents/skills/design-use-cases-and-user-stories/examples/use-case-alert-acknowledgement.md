# Use Case подтверждения алерта

Пример из `wiegers_sa_reference.md`, § 7.1, UC-004 (строки 943–1023).

```text
USE CASE SPECIFICATION

UC ID: UC-004
Название: Подтверждение алерта (Acknowledge Alert)
Версия: 1.2
Автор: [Имя SA]
Дата: ДД.ММ.ГГГГ
Статус: Approved

1. КРАТКОЕ ОПИСАНИЕ
Инженер NOC подтверждает активный алерт, указывая, что проблема
принята в работу. Это предотвращает повторные эскалации по данному
алерту и информирует других инженеров.

2. АКТОРЫ
Основной актор: NOC-инженер (зарегистрированный пользователь с ролью
                Engineer или Admin)
Вторичные акторы: Система нотификаций (получает событие),
                  ITSM система (создаётся тикет)

3. ПРЕДУСЛОВИЯ
- Пользователь авторизован в NMS
- В системе существует алерт в статусе ACTIVE или NEW
- Пользователь имеет право на подтверждение алертов (роль ≥ Engineer)

4. ПОСТУСЛОВИЯ (при успехе)
- Статус алерта изменён на ACKNOWLEDGED
- В журнал алерта добавлена запись (пользователь, время, комментарий)
- Таймер эскалации сброшен
- Другие инженеры видят, кто взял алерт в работу

5. ОСНОВНОЙ ПОТОК (Happy Path)
1. Инженер открывает список активных алертов
2. Инженер выбирает алерт для подтверждения
3. Система отображает детали алерта и поле для комментария
4. Инженер вводит комментарий (обязательно для CRITICAL)
5. Инженер нажимает кнопку "Подтвердить" (Acknowledge)
6. Система валидирует данные
7. Система изменяет статус алерта на ACKNOWLEDGED
8. Система обновляет журнал алерта
9. Система отправляет событие в систему нотификаций
10. Система отображает обновлённый алерт со статусом ACKNOWLEDGED

6. АЛЬТЕРНАТИВНЫЕ ПОТОКИ

6а. Алерт уже закрыт (CLEARED)
  На шаге 2: если алерт уже CLEARED или ACKNOWLEDGED другим инженером,
  система отображает уведомление: "Алерт уже обработан инженером [Имя]".
  Use Case завершается без изменений.

6б. Пустой комментарий для CRITICAL-алерта
  На шаге 6: если поле комментария пустое и уровень CRITICAL,
  система отображает: "Для CRITICAL-алертов комментарий обязателен."
  Инженер возвращается к шагу 4.

6в. Потеря соединения при подтверждении
  На шаге 7: если соединение разорвалось до завершения транзакции,
  система отображает ошибку: "Не удалось подтвердить алерт.
  Проверьте соединение и повторите."
  Статус алерта не изменяется (транзакция откатывается).

7. ИСКЛЮЧЕНИЯ
  E1. Сессия пользователя истекла → перенаправление на страницу входа
  E2. Нет прав на операцию → сообщение об ошибке 403

8. ТРЕБОВАНИЯ К ПРОИЗВОДИТЕЛЬНОСТИ
  Шаг 7–10 должен завершиться ≤ 2 секунд.

9. БИЗНЕС-ПРАВИЛА
  BR-ACK-01: Один алерт может подтвердить только один инженер.
  BR-ACK-02: CRITICAL-алерты требуют обязательный комментарий.
  BR-ACK-03: Подтверждение сбрасывает таймер эскалации.

10. OPEN ISSUES
  - TBD: интеграция с ITSM (автосоздание тикета) — решение к 15.02.2025

11. СВЯЗИ
  Включает (include): UC-001 Авторизация
  Расширяет (extend): UC-005 Эскалация алерта
  Связан с FR: FR-012, FR-013
  Связан с US: US-002
```

## Проверка по примеру

- Сверь цель и предусловия с основным потоком. Если алерт был активен при входе, уточни момент, когда он мог закрыться или быть подтверждён другим инженером.
- Для ветки 6а уточни, одинаков ли текст для CLEARED и ACKNOWLEDGED и всегда ли известно имя инженера. У 6б есть точка возврата. У 6в описан результат, а точный порядок повтора может потребовать уточнения.
- Сопоставь шаги со всеми постусловиями. Сброс таймера указан в постусловиях и бизнес-правилах. Проверь, виден ли момент сброса в потоке. ITSM указан среди участников и как открытый вопрос. Уточни статус интеграции.
- Авторизация одновременно фигурирует как предусловие и связь include. Уточни, вызывается ли UC-001 при выполнении этого сценария. В § 11.1 показаны другие отношения, включая обратное направление связи с эскалацией. Согласуй граф и текст для текущего проекта.

# Gherkin для работы с алертами

Пример из `wiegers_sa_reference.md`, § 5.3, формат 1, генерация и управление алертами (строки 563–618).

```gherkin
Feature: Генерация и управление алертами
  Система мониторинга должна генерировать алерты при
  обнаружении проблем с сетевыми устройствами.

  Background:
    Given устройство с ID "RTR-MSK-001" зарегистрировано в NMS
    And политика мониторинга настроена: порог CPU > 90% = MAJOR алерт

  Scenario: Генерация алерта при превышении порога CPU
    Given устройство "RTR-MSK-001" работает нормально (CPU 40%)
    When метрика CPU устройства "RTR-MSK-001" превышает 90%
    And это состояние сохраняется более 2 минут
    Then система должна создать алерт с серьёзностью "MAJOR"
    And алерт должен содержать: ID устройства, метрику, текущее
        значение, порог, timestamp
    And алерт должен появиться в дашборде не позже чем через 30 секунд
    And должно быть отправлено уведомление дежурному инженеру

  Scenario: Автоматическое закрытие алерта при нормализации
    Given активен алерт "MAJOR" по CPU для "RTR-MSK-001"
    When метрика CPU опускается ниже 80%
    And это состояние сохраняется более 5 минут
    Then алерт должен автоматически закрыться
    And статус алерта изменяется на "CLEARED"
    And в историю алерта добавляется запись о причине закрытия
    And инженеру приходит уведомление о нормализации

  Scenario: Подтверждение алерта инженером
    Given активен алерт "CRITICAL" с ID "ALT-20250101-001"
    And инженер авторизован в системе с ролью "NOC Engineer"
    When инженер нажимает кнопку "Acknowledge"
    And вводит комментарий "Начал расследование, escalation team уведомлена"
    Then статус алерта изменяется на "ACKNOWLEDGED"
    And в журнал алерта добавляется: имя инженера, timestamp, комментарий
    And таймер эскалации (15 мин) сбрасывается

  Scenario: Блокировка подтверждения без комментария
    Given активен алерт уровня CRITICAL
    When инженер нажимает "Acknowledge" без ввода комментария
    Then кнопка "Подтвердить" остаётся неактивной
    And отображается подсказка: "Для алертов CRITICAL комментарий обязателен"

  Scenario Outline: Маппинг серьёзности алертов
    Given поступает SNMP-трап с severity "<trap_severity>"
    When система обрабатывает трап
    Then алерт создаётся с серьёзностью "<alert_severity>"

    Examples:
      | trap_severity | alert_severity |
      | emergencies   | CRITICAL       |
      | alerts        | CRITICAL       |
      | critical      | MAJOR          |
      | errors        | MAJOR          |
      | warnings      | MINOR          |
      | notifications | WARNING        |
      | informational | INFO           |
```

## Проверка по примеру

- Сопоставь Given с правами и стартовым состоянием, When с действием или событием, Then со статусом, журналом, уведомлением и временем. Проверь, применим ли общий Background к каждому сценарию, включая маппинг трапов.
- Для строгих порогов сравни границу и соседние значения. Для временного ожидания уточни событие, от которого измеряется время. В Scenario Outline каждая строка таблицы даёт отдельную проверку.
- Здесь UI блокирует подтверждение CRITICAL-алерта без комментария, тогда как UC-004 в § 7.1 описывает отказ при валидации. Уточни, нужны ли оба уровня проверки и как выразить ожидаемое поведение.
- Переносы строк внутри шагов сохранены из справочника. Для исполняемого файла .feature запиши каждый шаг на одной строке.

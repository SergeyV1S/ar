# Классификация требований

| Что сказано в источнике | Как использовать |
|---|---|
| Организация хочет изменить показатель или добиться определённого эффекта | БТ с критерием достижения результата |
| Роль должна иметь возможность выполнить задачу | Пользовательская потребность. Из неё выдели подтверждённое обязательство системы и свяжи ФТ с потребностью |
| Система отвечает на событие, выполняет проверку, преобразует данные или меняет состояние | ФТ с наблюдаемым результатом |
| Система должна выдерживать заданную нагрузку, укладываться в порог или работать в обязательной среде | НФТ с метрикой или проверкой соответствия |

Уровни связаны между собой. БТ объясняет цель изменения, пользовательская потребность описывает задачу участника процесса, ФТ задаёт ответ системы, НФТ задаёт проверяемое качество или ограничение в указанной области. Для одной функции может действовать несколько НФТ. Бизнес-цель проверяй по материалам спонсора или владельца продукта, пользовательскую задачу — по материалам операторов и других участников процесса, поведение и ограничения — по сценариям, правилам и спецификациям.

Например, «пользователь должен восстанавливать доступ без обращения в поддержку» описывает пользовательскую задачу. Способ сброса пароля и реакция системы на запрос становятся ФТ, когда их определяют материалы. Аналогично, из задачи администратора настраивать пороги без разработчика можно извлечь обязательство системы предоставлять настройку указанной роли.

Бизнес-правило может определять реакцию системы, например обязательность комментария при подтверждении критического алерта. Оно также может задавать ограничение, например минимальный срок хранения журналов. Сохрани связь с правилом и зафиксируй его применимое следствие в ФТ или НФТ.

В интеграции отдельно выделяй обязательство обмениваться данными, ограничение на обязательный протокол или формат и метрику скорости обмена, если каждое из них задано. Например, получение топологии из OSS задаёт поведение, REST API может быть обязательным способом обмена, а предположение о доступности OSS 99,9% требует подтверждения как внешняя зависимость. Системное ограничение может касаться всей целевой среды, включая оборудование и ПО.

Для смешанного утверждения проверь, можно ли принять поведение при нарушении порога качества или подтвердить одно из заявленных действий отдельно. В таком случае зафиксируй независимые обязательства отдельными строками, сохранив их общий контекст.

# Разбор составного требования к генерации алерта

В учебном сценарии превышение порога CPU более двух минут ведёт к созданию алерта MAJOR, появлению его в дашборде и уведомлению инженера. У этих результатов есть самостоятельные проверки.

| ID | Требование | Критерий приёмки |
|---|---|---|
| ФТ-01 | Если загрузка CPU зарегистрированного устройства превышает 90% дольше 2 минут, система должна создать алерт MAJOR с ID устройства, метрикой, текущим значением, порогом и временем. | Дано зарегистрированное устройство с такой политикой мониторинга. Когда загрузка CPU остаётся выше 90% дольше 2 минут, появляется алерт MAJOR с указанными полями. |
| ФТ-02 | Система должна отображать созданный по этому правилу алерт в дашборде. | Когда по правилу создан алерт MAJOR, этот алерт отображается в дашборде. |
| ФТ-03 | Система должна уведомлять дежурного инженера об алерте, созданном по этому правилу. | Когда по правилу создан алерт MAJOR, дежурный инженер получает уведомление об алерте. |

Для задержки отображения задан верхний предел 30 секунд. Чтобы записать отдельное НФТ с однозначным критерием, уточни, от какого события отсчитывается интервал. Сохрани строгие границы «выше 90%» и «дольше 2 минут». Канал уведомления в этом сценарии не задан.

В отдельном сценарии алерт CRITICAL создаётся при обнаружении потери связи с управляемым устройством. Его НФТ ограничивает время именно **создания** алерта, не более 30 секунд от обнаружения потери связи. Проверь, к какой операции относится каждый порог.
